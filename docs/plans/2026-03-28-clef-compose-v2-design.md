# Clef Compose v2 设计文档

> 基于 CoComposer 论文启发，将 clef-compose 从"简谱 + Clef JSON"管线迁移到"ABC + music21 + mido"多工具协作架构。

## 1. 背景与动机

### 1.1 当前架构

- **5 个 Agent**: Composer(opus) / Harmonist / Rhythmist / Orchestrator / Reviewer(sonnet)
- **7 步管线**: 需求解析 → 风格分析 → 交互收集 → 规划 → 方向小样 → 完整初版 → 完整生产 → 自评输出
- **中间格式**: 简谱(jianpu) + Clef JSON v2.0
- **自建脚本**: jianpu_to_json.py, validate_clef.py, generate_expression.py

### 1.2 核心问题

1. **简谱格式训练不足** — LLM 对简谱的训练数据极少，导致格式错误率高（八度标记遗漏、附点拍数不平衡、模进跨八度不同步）
2. **多文件合并复杂** — 6+ 个中间 JSON 文件需要手动合并为 final.json
3. **技术检查混入创作** — Reviewer 同时做格式验证和音乐性评价，两个目标冲突
4. **静态反馈调度** — 反馈映射表是硬编码的，无法动态决定"改哪个 Agent 的什么内容"
5. **自建脚本维护负担** — validate_clef.py 等脚本需要持续维护，且功能被成熟工具覆盖

### 1.3 CoComposer 论文启发

| 启发 | 来源 | 价值 |
|------|------|------|
| Revision Agent（最小干预修正） | CoComposer 5 Agent 架构 | 解耦格式修正与创作 |
| Leader 驱动迭代 | CoComposer Phase 2 | 从静态映射表升级到动态调度 |
| ABC 记谱法 | CoComposer + ComposerX | LLM 海量训练数据，格式错误率低 |
| Feedback Analysis Agent | CoComposer Future Work | 将用户碎片化反馈转化为结构化指令 |
| Memory Mechanism | CoComposer Future Work | 跨会话记录用户偏好，逐步个性化 |

## 2. 架构概述

### 2.1 工具链：ABC + music21 + mido（方案 D）

```
Composer/Harmonist/Rhythmist → ABC（音符+和弦+节奏）
                                        ↓
Orchestrator → ABC 力度标记 + expression_plan.json
                                        ↓
Merger (Python) → score.abc（合并所有声部）
                                        ↓
music21 validate → ValidationReport（技术验证）
                                        ↓
abc_to_midi(score.abc) → base.mid
                                        ↓
mido inject (base.mid + expression_plan.json) → final.mid
                                        ↓
Godot 直接导入 .mid
```

**分工：**
- **ABC** — Agent 创作输出的"共同语言"
- **music21** — 脑子（分析、验证、乐理检查）
- **mido** — 手（精确操控每个 MIDI 事件：CC/pitch bend）
- **abc_to_midi.py** — 桥梁（ABC → 基础 MIDI，自写，MIT 许可）

### 2.2 为什么选方案 D

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A: music21 万能枢纽 | 单依赖 | MIDI 表现力输出有硬伤（不支持 CC 曲线/pitch bend） | ❌ |
| B: ABC + JSON 双层 | 最小改动 | 两套格式并存增加复杂度 | ⚠️ |
| C: MusicXML + MuseScore | 质量最高 | 依赖 MuseScore 安装，CI 不友好 | ❌ |
| **D: ABC + music21 + mido** | **分工明确，各取所长** | **需写胶水代码** | **✅ 采用** |

### 2.3 与当前架构对比

| 维度 | 当前 | v2 |
|------|------|----|
| 中间文件数 | 6+ 个 JSON/jianpu | 1 个 ABC + 1 个 expression_plan.json |
| 合并步骤 | Step 5 手动合并所有轨道 | Merger 自动合并（ABC 多声部） |
| 格式验证 | validate_clef.py（自建） | music21 + abc2midi（成熟） |
| 迭代机制 | 固定管线 + 静态反馈映射表 | Leader 驱动 + 动态反馈决策 |
| 表现力注入 | generate_expression.py → Clef JSON | mido 精确注入 MIDI 事件 |
| 技术分析 | Reviewer 手动做 | music21 自动做（调性/音域/声部进行） |
| 自建脚本 | 3 个 | 1 个 mido 注入脚本（替代 3 个） |
| 总步骤 | 7 步 | 4 步 |
| Godot 导入 | MidiReader 读 Clef JSON | MidiStream Player 直接播放 .mid |

## 3. ABC 格式规范

### 3.1 标准格式示例

```abc
%%abc-version 2.1
X:1
T:Boss Battle
C:Generated by Clef Compose
M:4/4
L:1/8
Q:1/4=140
K:D

%%MIDI channel 1
%%MIDI program 73
V:1 name="Flute" clef=treble
|: "D" d2 f2 a2 f2 | "G" g2 b2 d'2 b2 :|

%%MIDI channel 2
%%MIDI program 48
V:2 name="Strings" clef=treble
|: "D"[FAc]2 [FAc]2 [GBd]2 [FAc]2 | "G"[GBd]2 [GBd]2 [d'FA]2 [GBd]2 :|

%%MIDI channel 3
%%MIDI program 32
V:3 name="Bass" clef=bass
|: "D"D,2 D,2 F,2 D,2 | "G"G,2 G,2 B,2 G,2 :|

%%MIDI channel 10
V:4 name="Drums" clef=perc
%%MIDI drummap B,, 36
%%MIDI drummap D, 38
%%MIDI drummap G, 49
%%MIDI drummap c 42
|: B,, z D, z | B,, B,, z z :|
```

### 3.2 格式约定

| 约定 | 规范 | 说明 |
|------|------|------|
| ABC 版本 | `%%abc-version 2.1` | 头部必须声明 |
| 调号 | `K:D`(大调) / `K:Dm`(小调) / `K:Ddor`(多利亚) | 符合 ABC 标准，不用 K:Dmaj |
| 速度 | `Q:1/4=140` | 标准写法 |
| 和弦标记 | `"D"` 放在该和弦第一拍前 | 供 music21 分析提取 |
| 和弦音 | `[FAc]` 与标记对齐 | 供播放 |
| 鼓声部 | `V:4` + `%%MIDI channel 10` + `%%MIDI drummap` | 使用固定 GM 映射表 |
| 谱号 | 每个声部**强制**声明 clef | treble/bass/perc |
| %%MIDI 范围 | **仅**用于通道/音色分配 | 不用于精细表现力（mido 负责） |
| 声部对齐 | **强制**所有声部小节数相同 | Merger 自动补休止符 |

### 3.3 GM 鼓音高映射表（固定）

| 音色 | ABC 音高 | GM Note | 说明 |
|------|---------|---------|------|
| 低音鼓 | `B,,` | 36 | Kick |
| 军鼓 | `D,` | 38 | Snare |
| 闭镲 | `c` | 42 | Closed Hi-hat |
| 开镲 | `d` | 46 | Open Hi-hat |
| 高汤姆 | `A,` | 50 | High Tom |
| 低汤姆 | `F,` | 47 | Low Tom |
| 吊镲 | `a` | 49 | Crash |
| 叮叮镲 | `g` | 53 | Ride |

## 3b. 风格参考（--ref 参数）

用户可以通过 `--ref` 参数提供 Clef JSON 文件作为风格参考（保留 v1 功能）：

```
/clef-compose Boss战音乐 --ref addons/clef/output/boss_battle.json
```

### 处理流程

1. **格式转换** — 如果参考文件是 Clef JSON，需先转换为 ABC（使用一个逆向转换脚本，或手动提供 ABC 版本）
2. **分析** — 使用 music21 解析参考 ABC，提取风格特征（调性、BPM、乐器、节奏密度、和弦进行模式）
3. **合并** — 多文件冲突检测 + 合并为 `style_profile.json`（格式与 v1 兼容）
4. **注入** — Composer/Harmonist/Rhythmist 读取 `style_profile.json` 作为创作约束

### 约束优先级

用户明确指定 > 多文件参考合并 > 单文件参考 > Skill 默认值

### 未来改进

可考虑直接支持 ABC 文件作为 --ref 输入，省去格式转换步骤。

## 3c. 依赖管理与安装

### Python 依赖

| 包 | 版本 | 用途 |
|----|------|------|
| music21 | >= 9.0 | ABC 解析、乐理分析、验证 |
| mido | >= 1.3 | MIDI 事件操控、CC/pitch bend 注入 |

### abc2midi → 自写 abc_to_midi.py

**原方案使用 abc2midi（GPL-3.0），存在许可证传染风险——打包 GPL 软件可能导致整个插件需要以 GPL 发布。**

**替代方案：用 mido 自写 ABC→MIDI 转换器。** 我们的 ABC 用法是严格定义的子集（Section 3 规范），转换器只需支持：
- 头部解析（M, L, Q, K, %%abc-version）
- V: 声部声明 + %%MIDI channel/program
- 基础音符（a-g, 八度标记 ̇/̣, 时值 2/4/8/16, 升降号 #/b）
- 和弦 [FAc]
- 休止符 z
- 力度标记 !pp! !mp! !f! !ff!
- 小节线 | / ||

估算约 300-500 行 Python，输出 `mido.MidiFile` 对象。

**修正后的依赖清单（全部 MIT 兼容）：**

| 依赖 | 许可证 | 用途 |
|------|--------|------|
| Python（PyInstaller 打包） | PSF | 运行时 |
| music21 | BSD-3-Clause | 乐理分析、验证 |
| mido | MIT | MIDI 读写、CC 注入、ABC→MIDI 转换 |
| 自写 abc_to_midi.py | MIT | 替代 abc2midi |

### 依赖检查脚本

```python
# scripts/check_dependencies.py
"""检查 clef-compose v2 所需的外部依赖是否已安装。"""
import importlib, shutil, sys

def check():
    issues = []

    # Python 包
    for pkg in ['music21', 'mido']:
        try:
            importlib.import_module(pkg)
        except ImportError:
            issues.append(f"Python 包 '{pkg}' 未安装。运行: pip install {pkg}")

    if issues:
        print("依赖检查未通过：")
        for i in issues:
            print(f"  - {i}")
        return False
    else:
        print("所有依赖已就绪。")
        return True

if __name__ == '__main__':
    sys.exit(0 if check() else 1)
```

该脚本在 Phase 1 开始时运行，未安装的依赖会给出具体的安装命令。

### Step 0: 需求解析 → plan.json

与当前 Step 0/1/2/R 合并简化。输出 `plan.json`，格式不变。

### Step 1: 方向小样（8-16 拍）

```
Composer → melody_sample.abc (V:1 only)
  ↓
简化版 Merger → 生成完整 sample.abc（头部 + 仅 V:1）
  ↓
music21 → 快速技术验证（秒级）
  ↓
Reviewer → 音乐质量审核
  ↓
abc2midi sample.abc → sample.mid
  ↓
用户试听 ← 通过 MidiStream Player 播放 sample.mid，确认方向
```

> **试听机制：** 用户通过项目内置的 MidiStream Player 直接播放 .mid 文件。系统将 sample.mid 复制到 `addons/clef/output/` 供 Godot 场景加载。

### Step 2: 完整创作（迭代循环）

```
Round 1: 创作生成
  Composer → V:1 旋律 ABC（首轮：基于 plan.json 独立生成，V:2 尚不存在）
  Harmonist → V:2 和声 ABC（基于 V:1 旋律）
  Rhythmist → V:3 低音 + V:4 鼓 ABC（基于 V:2 和弦）
  Merger → score.abc（合并所有声部）

  注意：首轮中三个 Agent 存在依赖链 Composer → Harmonist → Rhythmist。
  实际执行时可以先并行生成 Composer 和 Harmonist（Harmonist 暂不读 V:1），
  再由 Harmonist 根据 V:1 调整，最后 Rhythmist 根据 V:2 生成。
  后续迭代轮中，所有 Agent 都可读取完整的 score.abc。

Round 2: 验证 + 审核
  music21 validate → validation_report.json
  Reviewer review → review_report.json
  确定性调度器 → 技术性错误派 Revision
  LLM Leader → 音乐性问题动态决策

  if iteration_complete:
    → 进入 Step 3
  else:
    → Agent 修改对应声部 → Merger 重新合并 → 回到 Round 2

（最多 N 轮，默认 3）
```

### Step 3: 表现力注入

```
Orchestrator → 在 score.abc 添加 !pp! !f! 等力度标记（修改 score.abc）
             → 生成 expression_plan.json
  ↓
abc_to_midi(score.abc) → base.mid
  ↓
inject_expression.py (base.mid + expression_plan.json) → final.mid
  ↓
复制到 addons/clef/output/
```

### Step 4: 自评 + 输出

使用统一评估系统（见 Section 7.3），生成分析报告。

> **试听机制：** 用户通过 MidiStream Player 播放 final.mid。如果用户给出修改意见，
> 通过 Section 6.8 的反馈机制处理，可能触发回到 Step 2 的局部修改。

## 5. Agent 角色

### 5.1 Agent 总览

| Agent | 模型 | 职责 | 输出 | 变化 |
|-------|------|------|------|------|
| Composer | opus | 旋律创作 | V:1 ABC 片段 | 格式 jianpu → ABC |
| Harmonist | sonnet | 和声编配 | V:2 ABC 片段 | 格式 JSON → ABC 声部 |
| Rhythmist | sonnet | 低音+鼓 | V:3 + V:4 ABC 片段 | 合并两个声部 |
| Orchestrator | sonnet | 表现力 | 力度标记 + expression_plan.json | 保留 JSON 但只用于 mido |
| Reviewer | sonnet | 音乐质量 | review_report.json | 专注音乐性，技术检查交给 music21 |
| **Revision** | haiku | 格式修正 | 完整 score.abc | **新增** |
| **Leader** | sonnet | 迭代调度 | tasks.json | **新增** |

### 5.2 共享上下文（所有 Agent）

```markdown
## 必读文件
- `.clef-work/plan.json` — 音乐规划（调性、BPM、段落、配器）
- `.clef-work/score.abc` — 当前完整乐谱（所有声部）
- `.claude/skills/clef-compose/theory.md` — 乐理知识

## 任务模式
- **完整生成**：从零创建声部，参考 plan.json 和已有声部
- **定向修改**：只修改 Leader 指定的小节范围，输出完整声部（含未修改小节）
  - 保持修改范围外的内容不变
  - 确保与前后小节衔接自然
  - 无法满足指令时输出注释 % NOTE: 无法完成，原因...

## 全局约束（不可违反）
1. 所有声部小节数必须相同，不足用 z 补齐
2. 所有声部使用头部 K: 声明的调号
3. 和弦标记("D")与和弦音([FAc])必须对应
4. 只输出指定声部，不输出头部，不修改其他声部
5. 定向修改时输出完整声部（含未修改小节），不是片段
```

### 5.3 Composer Agent

```markdown
你是 Composer，专业的游戏音乐作曲家。

## 任务
根据 plan.json 和 score.abc 中已有的和弦声部（V:2），生成/修改旋律声部（V:1）。
- 首轮：V:2 为空，根据 plan.json 调性写旋律
- 迭代轮：读取 V:2 和弦标记，确保旋律与和弦配合

## 输出
只输出 V:1 声部的 ABC 片段（不包含头部），Merger 负责合并。

## 约束
- 动机发展：2-4 音符核心动机，至少 2 种发展手法（重复/变奏/模进/倒影）
- 大跳处理：>5 半音需插入经过音，段落开头允许 1 个大跳但需级进收回
- 段落过渡：音区变化 ≤ 3 半音，级进过渡
- 乐句衔接：弱起、经过音连接、只在段落结尾用终止式
- 音域：1.5 八度内（具体范围参考 plan.json 乐器配置）
- 高潮：B/C 段最高音，配合力度标记
- 节奏变化：长短交替、断连对比、切分音，至少 3 种时值
```

### 5.4 Harmonist Agent

```markdown
你是 Harmonist，专业的和声编配专家。

## 任务
根据 plan.json 和 score.abc 中的旋律声部（V:1），生成/修改和声声部（V:2）。

## 输出
只输出 V:2 声部的 ABC 片段。

## 约束
- 和弦标记("D")与和弦音([FAc])同时出现且对齐
- 强拍和弦音支撑旋律
- 和弦进行遵循功能逻辑（T→S→D→T）
- 声部进行：共同音保持，非共同音级进
- 与旋律声部（V:1）之间避免平行五八度
- 与低音声部（V:3）之间也需注意声部进行
```

### 5.5 Rhythmist Agent

```markdown
你是 Rhythmist，节奏和低音专家。

## 任务
生成低音声部（V:3）和鼓声部（V:4）。

## 输出
输出两个声部的 ABC 片段（V:3 和 V:4），按顺序。

## 鼓音高映射（固定）
低音鼓=B,, 军鼓=D, 闭镲=c 开镲=d 高汤姆=A, 低汤姆=F, 吊镲=a 叮叮镲=g

## 约束
- 低音：优先选择和弦根音或五音，避免与旋律形成不协和音程
- 鼓：根据段落能量需求动态调整密度（非固定 A 简约/B 加花）
- 低音参考 V:2 和弦标记
- 所有声部小节数与 V:1 一致
```

### 5.6 Revision Agent（新增）

```markdown
你是 Revision，ABC 格式修正专家。

## 任务
修正 score.abc 中的格式错误，绝不修改创作内容。

## 修正范围（仅限以下）
- 小节时值不匹配 → 调整音符时值或添加 z 休止符
- 缺少 %%MIDI 指令 → 补充缺失的通道和音色
- 声部小节数不对齐 → 补齐休止符
- ABC 语法错误 → 修正格式

## 输入
- score.abc — 当前乐谱
- validation_report.json — music21/abc2midi 的错误日志（若提供）

## 禁止
- 不修改音符、和弦、节奏型
- 不改变创作意图
- 不添加/删除音符
- 不添加表现力指令（%%MIDI vol 等）

## 输出
修正后的完整 score.abc
```

### 5.7 Leader Agent（新增）

```markdown
你是 Leader，音乐制作团队的总指挥。

## 输入
- review_report.json — Reviewer 的音乐质量评估
- validation_report.json — music21 的技术验证
- user_feedback.json — 用户反馈（若存在）

## 决策规则
1. 优先级排序 — 和声 > 旋律（和弦改了旋律需同步），节奏独立
2. 任务合并 — 同一声部同一段落的多个问题合并为一个任务
3. 依赖关系 — 声部进行问题需先 Harmonist 再 Composer（depends_on）
4. 任务上限 — 一轮最多 3 个任务，避免过度修改
5. 终止条件 — 无技术性 FAIL + 总分 ≥ 7.5 + 所有维度 ≥ 6

## 输出（必须为合法 JSON）
{
  "tasks": [
    {"agent": "harmonist", "scope": "V:2, bars 5-8",
     "instruction": "将第5小节和弦从D改为G，避免平行五度",
     "depends_on": null},
    {"agent": "composer", "scope": "V:1, bars 5-8",
     "instruction": "根据新和弦调整旋律音",
     "depends_on": "harmonist"}
  ],
  "iteration_complete": false,
  "reasoning": "存在平行五度，需先修改和声再同步旋律"
}
```

### 5.8 Reviewer Agent（修订）

```markdown
你是 Reviewer，旋律和乐谱审核专家。

## 任务
读取 score.abc，从音乐质量维度进行评估。技术格式检查由 music21 自动完成。

## 评审维度
- 旋律质量：动机辨识度、发展手法、音域控制、高潮位置
- 和声质量：进行流畅度、张力释放、旋律和声配合
```

### 6.5 Leader 输出稳定性

LLM 输出的 JSON 可能格式错误、字段缺失或包含无效 agent 名称，需要在调度器中实现多层防御。

#### Leader Prompt 约束

```markdown
## 输出约束（强制）
- 只输出 JSON，不要添加 markdown 代码块标记、额外文本或解释
- agent 字段只能是: composer, harmonist, rhythmist, orchestrator, revision
- scope 格式: "V:N, bars X-Y" 或 "V:N, bars X"（单小节）
- instruction 必须非空
- depends_on 只能为 null 或其他任务的 agent 名称
```

#### 调度器 Fallback 策略

```python
VALID_AGENTS = {'composer', 'harmonist', 'rhythmist', 'orchestrator', 'revision'}
SCOPE_PATTERN = re.compile(r'V:(\d),\s*bars?\s*(\d+)(?:-(\d+))?')

def parse_leader_output(raw: str) -> list[Task]:
    # 1. JSON 解析失败 → fallback
    try:
        data = json.loads(raw)
    except json.JSONDecodeError:
        log.error("Leader JSON parse failed", raw=raw)
        return []  # 空列表 = 本轮不修改，继续评估

    tasks = []
    for t in data.get('tasks', []):
        # 2. agent 名称无效 → 跳过并警告
        if t.get('agent') not in VALID_AGENTS:
            log.warn(f"Unknown agent: {t.get('agent')}")
            continue

        # 3. scope 格式不规范 → 正则提取，失败则用默认范围
        scope = t.get('scope', '')
        match = SCOPE_PATTERN.match(scope)
        if match:
            voice = int(match.group(1))
            bar_start = int(match.group(2))
            bar_end = int(match.group(3)) if match.group(3) else bar_start
        else:
            log.warn(f"Invalid scope: {scope}, using full section")
            voice, bar_start, bar_end = None, None, None

        # 4. instruction 为空 → 跳过
        if not t.get('instruction', '').strip():
            log.warn("Empty instruction, skipping task")
            continue

        tasks.append(Task(
            agent=t['agent'], voice=voice,
            bar_start=bar_start, bar_end=bar_end,
            instruction=t['instruction'],
            depends_on=t.get('depends_on')
        ))

    # 5. 任务数量限制
    return tasks[:3]
```

### 6.6 健壮性设计

| 风险 | 对策 |
|------|------|
| Leader 输出非 JSON | fallback：空任务列表，本轮不修改创作 |
| Leader agent 名称无效 | 跳过该任务，记录警告 |
| Leader scope 格式错误 | 正则提取，失败则用默认范围（整段） |
| Leader instruction 为空 | 跳过该任务 |
| 同一问题反复指派 | 记录历史任务，相同 scope+instruction 跳过 |
| Agent 修改失败 | 记录失败，跳过该任务，继续执行队列 |
| 循环依赖 | 拓扑排序检测，报错终止迭代 |
| 超过最大迭代次数 | 强制终止，输出当前最佳版本 + 未解决问题清单 |

#### extract_solo.py 设计

```python
# scripts/extract_solo.py
def extract_solo(mid_path: str, start_sec: float, end_sec: float,
                 output_dir: str) -> list[str]:
    """从 MIDI 中提取指定时间段，按轨道分离为 solo 文件。"""
    mid = mido.MidiFile(mid_path)
    bpm = get_tempo(mid)
    start_tick = sec_to_tick(start_sec, mid.ticks_per_beat, bpm)
    end_tick = sec_to_tick(end_sec, mid.ticks_per_beat, bpm)

    solo_files = []
    for i, track in enumerate(mid.tracks):
        # 过滤该轨道在时间范围内的所有事件
        filtered = [e for e in track
                    if start_tick <= e.time <= end_tick]
        if not filtered:
            continue

        # 创建只有该轨道的 MIDI 文件
        solo_mid = mido.MidiFile()
        solo_mid.ticks_per_beat = mid.ticks_per_beat
        solo_track = mido.MidiTrack(filtered)
        # 重新映射时间，使片段从 0 开始
        offset_time(solo_track, -start_tick)
        solo_mid.tracks.append(solo_track)

        name = get_track_name(track, i)  # 从 MIDI track name 获取
        path = f"{output_dir}/solo_{name}_{int(start_sec)}-{int(end_sec)}s.mid"
        solo_mid.save(path)
        solo_files.append(path)

    return solo_files
```

### 7.1 功能

```python
# scripts/validate_abc.py
def validate(abc_path: str, plan: dict) -> ValidationReport:
    score = music21.converter.parse(abc_path)
    report = ValidationReport()

    # 1. 调性一致性
    detected_key = score.analyze('key')
    report.check('key_consistency', expected=plan['key'], actual=str(detected_key))

    # 2. 音域检查（每个声部 vs 乐器范围）
    for part in score.parts:
        pitches = [n.pitch.midi for n in part.flatten().notes]
        report.check('range', part=part.id,
                     actual=(min(pitches), max(pitches)),
                     expected=INSTRUMENT_RANGES[plan['orchestration'][part.id]])

    # 3. 大跳检测（旋律声部）
    melody = score.parts[0]
    for n1, n2 in zip(melody.notes, melody.notes[1:]):
        interval = music21.interval.Interval(n1.pitch, n2.pitch)
        if interval.semitones > 5:
            report.warn('large_leap', beat=n2.beat,
                        semitones=interval.semitones)

    # 4. 声部进行分析（新增能力）
    chords = score.chordify()
    for c1, c2 in zip(chords, chords[1:]):
        if has_parallel_5th_or_8ve(c1, c2):
            report.warn('parallel_motion', beat=c2.beat)

    # 5. 小节时值验证
    for measure in score.parts[0].getElementsByClass('Measure'):
        actual = measure.duration.quarterLength
        expected = score.metadata.timeSignature.beatCount
        if not is_close(actual, expected):
            report.fail('measure_duration',
                       measure=measure.number,
                       expected=expected, actual=actual)

    # 6. 声部小节数对齐
    counts = [len(p.getElementsByClass('Measure')) for p in score.parts]
    if len(set(counts)) > 1:
        report.fail('voice_alignment', counts=counts)

    return report
```

### 7.3 统一评估系统（自评）

v2 将当前 `self_eval_checklist.json` 和 Reviewer Agent 的评估合并为统一系统，避免重复评估。

#### 分层评估

| 层级 | 执行者 | 检查内容 | 数据来源 |
|------|--------|---------|---------|
| 自动量化 | music21 | 音域、调性、小节时值、声部对齐、大跳检测 | score.abc + plan.json |
| 音乐性 | Reviewer Agent | 动机质量、情感表达、风格一致性、乐句衔接 | score.abc + plan.json |

#### 评分公式（保留 v1）

```
总分 = Σ(维度得分[i] × 权重[i])

维度权重：melody 0.25, harmony 0.25, rhythm 0.20, expression 0.15, structure 0.15

每个维度得分 = 该维度检查项之和（每项 0/1/2 分，满分 10 分）
```

#### 维度定义（精简版，从 v1 迁移）

**自动量化检查（music21，每项 0/2 分）：**
- 旋律音域合规（vs 乐器范围）
- 旋律大跳处理（>5 半音有经过音）
- 小节时值正确
- 声部小节数对齐
- 调性一致性

**音乐性检查（Reviewer，每项 0/1/2 分）：**
- 旋律：动机辨识度、发展手法、乐句衔接、高潮位置
- 和声：进行流畅度、旋律和声配合、低音声部进行
- 节奏：律动感、段落变化、节奏层次、过渡 fills
- 表现力：velocity 范围、动态曲线、pitch bend 使用、CC 表现力
- 结构：形式清晰度、段落对比、起承转合、收束感

```python
# scripts/inject_expression.py
def inject(base_mid_path: str, plan_path: str, output_path: str):
    mid = mido.MidiFile(base_mid_path)
    plan = json.load(open(plan_path))
    track_map = map_tracks_by_channel(mid)

    for track_plan in plan['tracks']:
        midi_track = track_map[track_plan['channel']]
        for event in track_plan['events']:
            tick = beat_to_tick(event['time_beats'], mid.ticks_per_beat)
            if event['type'] == 'cc':
                midi_track.events.append(mido.Message('control_change',
                    channel=track_plan['channel']-1,
                    control=event['control'], value=event['value'],
                    time=tick))
            elif event['type'] == 'pitch_bend':
                midi_track.events.append(mido.Message('pitchwheel',
                    channel=track_plan['channel']-1,
                    pitch=event['value'], time=tick))

    mid.save(output_path)
```

1. **时间单位：拍（beats）** — 与 ABC 和 Clef JSON v2.0 一致，mido 内部转换到 tick
2. **Pitch bend 成对** — 每个弯音事件必须有归零事件（8192）
3. **CC 曲线** — Orchestrator 定义关键点，可扩展为线性插值

### 9.1 职责

合并各 Agent 输出的声部片段为完整 score.abc，处理头部生成、声部拼接、小节对齐。

### 9.2 两种模式

**完整合并模式（Step 2）：** 合并所有 4 个声部
**单声部模式（Step 1）：** 只合并 V:1 + 头部（用于方向小样试听）

### 9.3 小节对齐算法

ABC 的小节边界由 `|` 标记。对齐需要：
1. 解析每个声部的小节数（统计 `|` 的数量，排除 `||` 段落边界）
2. 找到最大小节数
3. 对不足的声部，在末尾追加 `| z2 z2 |` 等休止符小节

```python
# scripts/merge_abc.py
import re
from pathlib import Path

def count_measures(abc_content: str) -> int:
    """统计 ABC 片段中的小节数。通过 | 数量计算，排除 || 和行内 |。"""
    # 移除段落边界 ||
    cleaned = abc_content.replace('||', '|')
    # 按行分割，统计每行末尾的 |
    lines = cleaned.strip().split('\n')
    total = 0
    for line in lines:
        # 只计算独立的小节线（行末或行内的 |），排除和弦内嵌
        bars = re.findall(r'(?<![^\s])\|(?![^\s])', line)
        # 更简单的方式：统计行内 | 的数量
        bar_count = line.count('|')
        total += bar_count
    return total

def pad_with_rests(abc_content: str, target_measures: int) -> str:
    """用休止符小节补齐到目标小节数。"""
    current = count_measures(abc_content)
    if current >= target_measures:
        return abc_content
    # 根据拍号确定每小节休止符
    # 默认 4/4 拍: z4 或 z2 z2
    missing = target_measures - current
    padding = ' | '.join(['z4'] * missing) + ' |'
    return abc_content.rstrip() + '\n' + padding

def merge(plan: dict, voice_fragments: dict[str, str],
          mode: str = 'full') -> str:
    """
    合并各 Agent 输出的声部片段为完整 score.abc。

    Args:
        plan: plan.json（提取头部信息）
        voice_fragments: {voice_id: abc_content}
        mode: 'full'（4声部）或 'solo'（仅V:1）
    """
    # 1. 生成公共头部
    header = generate_header(plan)

    # 2. 确定参与声部
    if mode == 'solo':
        voices_to_merge = ['V:1']
    else:
        voices_to_merge = ['V:1', 'V:2', 'V:3', 'V:4']

    voices = []
    for vid in voices_to_merge:
        if vid in voice_fragments:
            voices.append(voice_fragments[vid])

    # 3. 对齐小节数（补休止符）
    if len(voices) > 1:
        measure_counts = [count_measures(v) for v in voices]
        target = max(measure_counts)
        voices = [pad_with_rests(v, target) for v in voices]

    # 4. 组装完整文件
    body = '\n\n'.join(voices)
    return header + '\n\n' + body

def generate_header(plan: dict) -> str:
    """从 plan.json 生成 ABC 公共头部。"""
    key = plan['key']  # e.g. "D major" → "D", "D minor" → "Dm"
    # 简化转换（实际需要更健壮的解析）
    if 'minor' in key.lower() or 'min' in key.lower():
        key_str = key.split()[0] + 'm'
    else:
        key_str = key.split()[0]

    return f"""%%abc-version 2.1
X:1
T:{plan.get('title', 'Untitled')}
C:Generated by Clef Compose v2
M:{plan['time_signature']}
L:1/8
Q:1/4={plan['bpm']}
K:{key_str}"""
```
