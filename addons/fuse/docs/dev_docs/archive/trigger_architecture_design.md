# Trigger系统架构设计文档

## 概述

本文档描述了Fuse插件中两个触发器类的设计理念和用途：
- `BaseTrigger` - 复杂触发器的抽象基类
- `Trigger` - 简单事件-动作连接的具体实现

## 架构设计

### 1. BaseTrigger (addons/fuse/core/base/base_trigger.gd)

**设计理念**: 提供一个功能完整的触发器框架，支持复杂的触发逻辑和状态管理。

**核心特性**:
- 抽象基类，需要子类继承实现
- 完整的信号系统 (triggered, conditions_failed, action_completed, finished)
- 高级功能支持：
  - 冷却时间管理
  - 条件系统 (Array[BaseCondition])
  - 局部变量容器 (VariableContainer)
  - 详细的状态跟踪
- 支持输入处理和物理处理
- 完整的生命周期管理

**使用场景**:
- 需要复杂触发逻辑的游戏机制
- 需要条件判断的触发器
- 需要状态管理和冷却时间的系统
- 需要自定义输入处理的触发器

### 2. Trigger (addons/fuse/core/trigger.gd)

**设计理念**: 提供简单直接的事件-动作连接机制。

**核心特性**:
- 具体实现类，直接可用
- 基于组合模式，使用event_definition资源
- 简洁的接口和实现
- 专注于事件监听和动作执行
- 包含编辑器模式检查

**使用场景**:
- 简单的事件-动作连接
- 快速原型开发
- 不需要复杂条件的触发逻辑
- 可视化脚本系统的基础组件

## 关键差异

| 特性 | BaseTrigger | Trigger |
|------|-------------|---------|
| 类型 | 抽象基类 | 具体实现类 |
| 设计模式 | 继承导向 | 组合模式 |
| 复杂度 | 高 | 低 |
| 条件系统 | ✓ | ✗ |
| 冷却时间 | ✓ | ✗ |
| 变量容器 | ✓ | ✗ |
| 信号系统 | 完整 | 简化 |
| 编辑器检查 | 需要 | 已实现 |

## 编辑器模式处理

为了确保两个类都不会在编辑器模式下意外触发，需要在BaseTrigger的_ready()方法中添加编辑器模式检查：

```gdscript
func _ready():
    # 检查是否在编辑器模式下，如果是则跳过初始化
    if Engine.is_editor_hint():
        _log_debug("编辑器模式下，跳过BaseTrigger初始化")
        return
    
    _setup_trigger()
    _initialize_local_variables()
    _log_debug("BaseTrigger ready")
```

## 最佳实践

### 何时使用BaseTrigger
- 需要复杂的触发条件
- 需要状态管理和冷却时间
- 需要自定义输入处理
- 构建可重用的触发器组件

### 何时使用Trigger
- 简单的事件-动作连接
- 快速原型和测试
- 可视化脚本系统
- 不需要复杂条件的场景

### 迁移指南
如果需要从Trigger升级到BaseTrigger：
1. 创建继承自BaseTrigger的新类
2. 将event_definition的逻辑转换为_setup_trigger()方法
3. 根据需要添加条件、冷却时间等高级功能
4. 更新信号连接逻辑

## 未来扩展

### 可能的改进方向
1. **统一接口**: 为两个类提供共同的基础接口
2. **组件化**: 将条件、冷却等功能模块化为独立组件
3. **可视化编辑**: 为BaseTrigger提供更好的编辑器支持
4. **性能优化**: 针对大量触发器的场景进行优化

### 兼容性考虑
- 保持两个类的独立性，避免相互依赖
- 确保API的向后兼容性
- 提供清晰的迁移路径

## 总结

BaseTrigger和Trigger代表了两种不同的设计哲学：
- BaseTrigger追求功能完整性和可扩展性
- Trigger追求简洁性和易用性

这种双轨设计允许开发者根据具体需求选择合适的工具，既保证了系统的灵活性，又保持了使用的简便性。
