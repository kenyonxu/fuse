# Fuse 指令与事件评估体系

**创建日期:** 2026-01-25
**版本:** 1.0
**适用范围:** Instruction 和 Event 开发优先级评估

## 概述

本文档定义了 Fuse 可视化编程系统中 Instruction（指令）和 Event（事件）的多维度评估体系，用于评估待开发功能的优先级，确保开发资源投入到最关键、最易用的功能上。

---

## 评估维度

### 1. 需求频率（Frequency）

**定义：** 该功能在游戏开发中的使用频率

**评分标准：**

| 分数 | 等级 | 描述 | 示例 |
|------|------|------|------|
| **5** | 极高频 | 几乎每个游戏都需要 | 移动节点、播放音效、检测输入 |
| **4** | 高频 | 大多数游戏都会用到 | 物理碰撞、动画播放、UI 控制 |
| **3** | 中频 | 约半数游戏会用到 | 存档系统、AI 导航、网络功能 |
| **2** | 低频 | 特定类型游戏需要 | 手柄支持、触摸输入、音频节拍 |
| **1** | 极低频 | 少数特殊场景需要 | 自定义状态机、复杂的序列事件 |

**评估要点：**
- 考虑游戏类型和规模
- 参考其他可视化编程工具的功能覆盖
- 考虑功能的基础性和通用性

---

### 2. 即用性（Ready-to-Use）

**定义：** 新建 Godot 工程后能否直接使用该功能，无需编写额外代码

**评分标准：**

| 分数 | 等级 | 描述 | 示例 |
|------|------|------|------|
| **5** | 完全即用 | 无需任何配置或代码 | `On Ready`、`Print`、`Wait` |
| **4** | 基本即用 | 需要简单配置（选择节点、设置参数） | `Set Position`、`Play Sound`、`Change Scene` |
| **3** | 部分依赖 | 需要用户提供简单脚本或场景 | `Run Node Function`、`Play Animation` |
| **2** | 高度依赖 | 需要用户提供复杂代码或场景 | `On Signal Emit`、`Raycast` |
| **1** | 完全依赖 | 几乎完全依赖用户代码实现 | `Custom Data Structure`、`Advanced AI` |

**评估要点：**
- 是否需要用户预先编写 GDScript
- 是否需要用户创建特定场景结构
- 是否需要用户配置复杂参数

---

### 3. 开发复杂度（Development Complexity）

**定义：** 实现该功能所需的技术难度和工作量

**评分标准：**

| 分数 | 等级 | 工作量 | 描述 | 示例 |
|------|------|--------|------|------|
| **1** | 极简单 | 0.5-1 天 | 直接包装 Godot API，无复杂逻辑 | `Print`、`Set Variable`、`Quit Game` |
| **2** | 简单 | 1-2 天 | 基本包装 + 简单验证 | `Set Position`、`Show/Hide UI`、`Get Delta Time` |
| **3** | 中等 | 3-5 天 | 需要处理多个 API、异步逻辑 | `Move By`、`Play Animation`、`Change Scene` |
| **4** | 复杂 | 1-2 周 | 涉及系统集成、复杂状态管理 | `For Loop`、`If/Else`、`On Variable Changed` |
| **5** | 极复杂 | 2-4 周 | 需要架构设计、多个子系统配合 | `For Each`、`On Multiple Conditions`、`Navigation Events` |

**评估要点：**
- 代码行数估算
- 涉及的 Godot 系统复杂度
- 是否需要特殊处理（编辑器集成、异步、缓存等）
- 测试和文档工作量

---

### 4. 学习曲线（Learning Curve）

**定义：** 用户理解和掌握该功能所需的时间

**评分标准：**

| 分数 | 等级 | 学习时间 | 描述 | 示例 |
|------|------|----------|------|------|
| **1** | 极易 | < 5 分钟 | 概念直观，无需解释 | `Print`、`On Ready`、`Wait` |
| **2** | 易 | 5-15 分钟 | 概念简单，稍作说明 | `Set Variable`、`Show UI`、`Play Sound` |
| **3** | 中等 | 15-30 分钟 | 需要理解相关概念 | `For Loop`、`If/Else`、`Instantiate Scene` |
| **4** | 难 | 30-60 分钟 | 需要理解多个概念组合 | `Raycast`、`State Machine`、`Animation Blending` |
| **5** | 极难 | > 1 小时 | 需要深入理解系统或架构 | `Navigation Events`、`Network Events`、`Custom Events` |

**评估要点：**
- 概念的抽象程度
- 参数数量和复杂度
- 是否需要理解 Godot 特定机制（信号、节点树、物理系统等）
- 是否容易出错

---

### 5. 性能影响（Performance Impact）

**定义：** 该功能对游戏运行时性能的影响程度

**评分标准：**

| 分数 | 等级 | 性能开销 | 描述 | 示例 |
|------|------|----------|------|------|
| **1** | 可忽略 | < 0.1 ms | 一次性执行，无持续开销 | `On Ready`、`Change Scene`、`Print` |
| **2** | 低 | 0.1-0.5 ms | 简单操作，偶尔调用 | `Set Variable`、`Play Sound`、`Show UI` |
| **3** | 中 | 0.5-2 ms | 正常操作，可能频繁调用 | `Set Position`、`Instantiate Scene`、`Collision Check` |
| **4** | 高 | 2-10 ms | 复杂操作，频繁调用需优化 | `For Loop`（大数据）、`On Process`、`Raycast` |
| **5** | 极高 | > 10 ms | 非常复杂，需特别谨慎 | `On Process`（每帧）、`Shape Cast`、`Pathfinding` |

**评估要点：**
- 是否每帧调用（_process / _physics_process）
- 是否涉及大量计算或内存分配
- 是否可优化（缓存、对象池等）
- 高频使用的场景下性能影响

---

### 6. 依赖性（Dependency）

**定义：** 该功能被其他功能依赖的程度，以及它依赖其他功能的程度

**评分标准：**

| 分数 | 等级 | 描述 | 示例 |
|------|------|------|------|
| **5** | 基础依赖 | 被多个功能依赖，是核心基础 | `For Loop`、`Set Position`、`变量系统` |
| **4** | 中度依赖 | 被 2-3 个功能依赖 | `If/Else`、`Instantiate Scene`、`Find Node` |
| **3** | 轻度依赖 | 被 1 个功能依赖 | `Change Scene`、`Play Animation` |
| **2** | 低依赖 | 依赖其他功能，但被依赖少 | `Break Loop`、`Continue Loop`、`Move By` |
| **1** | 无依赖 | 独立功能，无依赖关系 | `Print`、`Quit Game`、`Pause Game` |

**评估要点：**
- 是否被其他多个功能依赖
- 是否是某个功能类的基础（如循环控制、变换操作）
- 依赖关系的深度（直接依赖 vs 间接依赖）
- 是否存在依赖链（A → B → C）

**依赖关系分析规则：**
1. **基础层功能**：被依赖度评 4-5 分（如 `For Loop`、`Set Position`）
2. **中间层功能**：依赖基础功能，又被高级功能依赖，评 3-4 分（如 `For Each`、`Move By`）
3. **高级层功能**：依赖其他功能，但很少被依赖，评 1-2 分（如 `Break Loop`、`Continue Loop`）
4. **独立功能**：无依赖关系，评 1 分（如 `Play Sound`、`Show UI`）

## 综合评分与优先级计算

### 加权方案

根据项目目标和当前阶段，可采用不同的加权方案：

#### 方案 A：平衡开发型（推荐）
适用于常规开发，兼顾速度、质量和易用性。

```
总分 = 需求频率 × 4.5
     + 即用性 × 3.5
     + (开发复杂度取反) × 2.5
     + (学习曲线取反) × 1.5
     + (性能影响取反) × 1.0
     + 依赖性 × 2.5
```

#### 方案 B：快速原型型
适用于快速迭代，优先开发简单和常用的功能。

```
总分 = 需求频率 × 5.0
     + 即用性 × 3.0
     + (开发复杂度取反) × 4.0
     + (学习曲线取反) × 1.5
     + (性能影响取反) × 1.0
     + 依赖性 × 1.5
```

#### 方案 C：用户体验优先型
适用于发布版本，优先优化易用性和性能。

```
总分 = 需求频率 × 3.0
     + 即用性 × 5.0
     + (开发复杂度取反) × 1.0
     + (学习曲线取反) × 3.5
     + (性能影响取反) × 3.5
     + 依赖性 × 1.5
```

**取反说明：**
- 开发复杂度、学习曲线、性能影响都是"越低越好"
- 取反后：新分数 = 6 - 原分数
- 例如：复杂度 4 分 → 取反后为 2 分

### 优先级分类

根据总分划分优先级（适用于方案 A）：

| 总分范围 | 优先级 | 开发策略 |
|---------|--------|----------|
| **70-78** | P0 - 紧急 | 立即开发，核心基础功能 |
| **60-69** | P1 - 高 | 优先开发，主力功能 |
| **50-59** | P2 - 中 | 计划开发，重要功能 |
| **40-49** | P3 - 低 | 延后开发，锦上添花 |
| **< 40** | P4 - 极低 | 暂缓开发，特殊需求 |

**说明：**
- P0 级功能通常是其他功能的基础依赖，必须优先开发
- P1 级功能是高频使用的核心功能
- P2 级功能是重要但可以稍后开发的功能
- P3 级功能是低频或复杂的功能
- P4 级功能是暂不开发的特殊需求

## 评估流程

### 步骤 1：收集信息

为每个 Instruction/Event 收集以下信息：
- 功能描述
- 使用场景
- 涉及的 Godot API
- 依赖关系
- 实现难点

### 步骤 2：独立评分

由 2-3 名开发者独立进行评分：
- 避免互相影响
- 参考评分标准
- 记录评分理由

### 步骤 3：讨论与校准

- 讨论评分差异较大的项
- 统一评分标准理解
- 必要时调整评分

### 步骤 4：计算总分

- 选择合适的加权方案
- 计算每个功能总分
- 排序生成优先级列表

### 步骤 5：优先级调整

根据以下因素微调优先级：
- **依赖关系**：某些功能需要先实现其他功能
- **技术风险**：高复杂度功能可能需要技术预研
- **用户反馈**：社区需求最高的功能可提升优先级
- **版本规划**：某些功能适合特定版本发布

## 示例评估

### 示例 1：Set Position（设置位置）

**功能描述：** 设置节点的全局或局部位置

**评分：**
- 需求频率：**5/5** - 几乎每个游戏都需要移动对象
- 即用性：**4/5** - 只需选择节点和设置位置
- 开发复杂度：**2/5** → 取反 **4/5** - 简单的属性设置
- 学习曲线：**2/5** → 取反 **4/5** - 概念简单
- 性能影响：**2/5** → 取反 **4/5** - 性能开销极小
- 依赖性：**5/5** - 被 Move By、Rotate By 等多个功能依赖

**计算（方案 A）：**
```
总分 = 5×4.5 + 4×3.5 + 4×2.5 + 4×1.5 + 4×1.0 + 5×2.5
     = 22.5 + 14.0 + 10.0 + 6.0 + 4.0 + 12.5
     = 69.0 (P1 - 高优先级)
```

**说明：** 作为基础变换操作，被多个功能依赖，评分较高，应优先开发。

---

### 示例 2：For Loop（循环）

**功能描述：** 重复执行指令序列固定次数

**评分：**
- 需求频率：**4/5** - 很多场景需要批量操作
- 即用性：**5/5** - 完全即用
- 开发复杂度：**4/5** → 取反 **2/5** - 需要嵌套指令管理
- 学习曲线：**3/5** → 取反 **3/5** - 需要理解循环概念
- 性能影响：**4/5** → 取反 **2/5** - 高频可能有性能问题
- 依赖性：**5/5** - 被 Break Loop、Continue Loop、For Each 等依赖

**计算（方案 A）：**
```
总分 = 4×4.5 + 5×3.5 + 2×2.5 + 3×1.5 + 2×1.0 + 5×2.5
     = 18.0 + 17.5 + 5.0 + 4.5 + 2.0 + 12.5
     = 59.5 (P2 - 中优先级，接近 P1)
```

**说明：** 虽然复杂度较高，但由于被多个循环控制功能依赖，评分提升到接近 P1，建议在基础功能完成后优先开发。

---

### 示例 3：On Process（每帧处理）

**功能描述：** 在每帧的 _process() 中触发

**评分：**
- 需求频率：**5/5** - 非常常用
- 即用性：**5/5** - 完全即用
- 开发复杂度：**2/5** → 取反 **4/5** - 实现简单
- 学习曲线：**2/5** → 取反 **4/5** - 概念简单
- 性能影响：**5/5** → 取反 **1/5** - 性能影响极大
- 依赖性：**1/5** - 独立功能，无依赖关系

**计算（方案 A）：**
```
总分 = 5×4.5 + 5×3.5 + 4×2.5 + 4×1.5 + 1×1.0 + 1×2.5
     = 22.5 + 17.5 + 10.0 + 6.0 + 1.0 + 2.5
     = 59.5 (P2 - 中优先级)
```

**说明：** 虽然需求极高，但性能风险大，需要文档明确说明使用场景和性能优化建议。

---

### 示例 4：Break Loop（跳出循环）

**功能描述：** 跳出当前循环

**评分：**
- 需求频率：**3/5** - 循环控制需要
- 即用性：**5/5** - 完全即用
- 开发复杂度：**2/5** → 取反 **4/5** - 实现简单
- 学习曲线：**2/5** → 取反 **4/5** - 概念简单
- 性能影响：**2/5** → 取反 **4/5** - 性能开销极小
- 依赖性：**2/5** - 依赖 For Loop/While Loop，但被依赖少

**计算（方案 A）：**
```
总分 = 3×4.5 + 5×3.5 + 4×2.5 + 4×1.5 + 4×1.0 + 2×2.5
     = 13.5 + 17.5 + 10.0 + 6.0 + 4.0 + 5.0
     = 56.0 (P2 - 中优先级)
```

**说明：** 虽然实现简单且易用，但依赖 For Loop，所以评分低于 For Loop (59.5)。必须先开发 For Loop，再开发此功能。

## 优先级调整规则

### 自动提升规则

以下情况可提升优先级：
1. **核心依赖** - 其他多个功能依赖此功能
2. **社区热点** - 用户反馈最多的功能
3. **技术验证** - 需要验证技术方案的功能

### 自动降低规则

以下情况可降低优先级：
1. **替代方案** - 有其他更简单的实现方式
2. **高风险** - 技术风险高，需要预研
3. **小众需求** - 仅特定类型游戏需要

### 依赖性处理

- 使用依赖图分析功能依赖关系
- 被依赖功能优先开发
- 可并行开发的功能标注

---

## 定期审查机制

### 月度审查

- 每月审查一次评估结果
- 根据开发进度和用户反馈调整
- 更新优先级列表

### 版本发布前审查

- 评估下一版本功能集
- 确保高优先级功能优先发布
- 平衡新功能和 bug 修复

## 总结

本评估体系通过 5 个核心维度，全面评估 Fuse 系统中 Instruction 和 Event 的开发优先级，确保：

1. ✅ **开发资源最大化** - 优先开发最需要、最易用的功能
