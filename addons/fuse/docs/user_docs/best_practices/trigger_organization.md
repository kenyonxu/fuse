# 触发器组织与竞态规避

## 概述

场景里的 Fuse 单元（Trigger / MultiEventTrigger / Runner）从十几个涨到上百个时，问题会从"怎么搭"变成"怎么管"：谁和谁共享数据、并发的触发顺序谁先谁后、出问题怎么定位。这篇实践指南讲两件事——**怎么理解竞态的真实边界**，以及**场景变大后怎么组织触发器**。

## 一、竞态的真实定义：写写才算

Topology 静态分析把跨单元的变量关联分成三型，这个分类就是竞态边界的权威定义：

| 关联型 | 含义 | 拓扑面板标记 |
|--------|------|--------------|
| 写 → 读 | 一个单元写变量，另一个读 | 📝 正常数据流 |
| 信号 | 一个单元发信号，另一个接收 | 🔗 正常通信 |
| **写 → 写** | **两个单元都写同一个变量** | 🔥 **竞态预警** |

**写读不是竞态，是依赖**——"血量更新 → 血条刷新"这种生产者-消费者关系正是事件系统的设计目标。真正的竞态是**两个 Trigger 写同一个变量**：两者触发顺序未定义，后写的覆盖先写的，而且没有任何报错——症状是"偶尔数值不对"，最难排查的一类 bug。

### 为什么写写危险

两个 Trigger 在同一帧或相邻帧触发（受击扣血 × 拾取回血），执行顺序取决于事件到达顺序、并行评估调度、甚至场景树位置。结果是变量值取决于"谁恰好后跑"——今天对的明天错，换台机器又对。

### 排查工具

Topology 主屏的竞态预警（黄色 🔥）会列出每对写写冲突和共享变量名。[Topology 指南](../Introductions/14-Topology拓扑主屏.md)有面板操作详解——本篇讲的是看到 🔥 之后怎么办。

## 二、竞态规避五法

按优先级从高到低，遇到 🔥 预警依次考虑：

### 1. 单一写者原则（首选）

**一个变量只允许一个 Trigger 写，其他全部只读。**这是最彻底的解法：

> 受击扣血和拾取回血都写 `hp` → 把"血量变更"收敛到一个 `ApplyHpDelta` Runner，受击和拾取都调用它传入正负增量。

调用方式用 `RunRunner` 指令（可视化里的"函数调用"）。写者收敛到一处后，顺序问题消失，血量逻辑的修改点也唯一了。

### 2. 作用域隔离

写写冲突发生在共享作用域时，考虑降格变量作用域：

- 两个敌人 Trigger 写"同一个"血量 → 其实它们该各写各的：血量从 GLOBAL 降为 **SCOPE**（每个敌人的子树一个容器），冲突自然消失
- 判断口诀：**写者属于不同对象实例时，变量就该跟着实例走**——SCOPE 容器挂在实例子树根上

作用域选型的完整规则见[变量系统指南](../guides/01-variable-system-guide.md)。

### 3. 触发控制：cooldown 与 trigger_once

冲突源于高频重复触发时，给写者加节流：

- `cooldown`（冷却）：区域内连续触碰只结算第一次——解决"站在陷阱里每帧扣血"
- `trigger_once`（只触发一次）：过场初始化类逻辑天然只需要跑一遍
- MultiEventTrigger 的触发控制是**每绑定独立配置**的，多事件共节点时逐个设置

参数在 Trigger 的 Inspector 触发控制组（`cooldown_mode: GLOBAL_COOLDOWN` 等）。注意这是**缓解**不是根治——两个低频写者仍然可能撞车，单一写者原则优先。

### 4. 事件语义替代状态轮询

写写冲突常来自"轮询式设计"：多个 Trigger 都 `OnInterval` 读状态再写标记。改用事件语义——状态变化方**发事件**（Event Bus / 自定义信号），消费方 `OnReceiveEvent` 收到再行动：

> 三个 Trigger 轮询 `game_state` 再各自写 `state_dirty` 标记 → 状态机 Trigger 切换时 `SendEvent("state_changed")`，三个消费者改为收事件后只做自己的事。

写者从三个变一个（状态机），消费方全部只读。

### 5. 合并进 MultiEventTrigger

同一节点上响应多个事件的几个 Trigger 若在写同一批变量，多半本该是一个逻辑：合并进 MultiEventTrigger 后，多事件在一个单元内**顺序执行**，写写变成单元内顺序语义（分支互斥或先来后到），竞态消除。右键场景树节点即可合并。

## 三、组织实践

### 选型递进不变

单元多了之后[触发器选型](../guides/02-trigger-selection-guide.md)的递进原则依然成立：简单信号用 Runner、需要事件过滤/触发控制用 Trigger、同节点多事件用 MultiEventTrigger。补充一条组织级原则：

- **按"对象"分组，不按"功能"分组**——玩家相关单元挂在玩家子树、敌人逻辑随敌人预制体走。SCOPE 隔离、拓扑可读性、场景拆分三个收益同时到手
- 跨对象通信走 Event Bus，不走"共享 GLOBAL 变量轮询"（见上节第 4 法）

### 命名

Trigger 节点名带上"对象 + 语义"：`Player_OnDamaged`、`Boss_Phase2_Entry`。拓扑面板、竞态预警、导出报告里显示的都是这个名字——`Area2D7 (Trigger)` 在竞态列表里等于没说。

### 终审流程

发布或里程碑前跑一遍（配合[调试指南](../guides/25-debugging-guide.md)的调试工作流）：

1. Topology 主屏 → 过滤"仅错误"，清零 error
2. 看竞态预警区（🔥），逐条按五法处置或确认无害
3. 导出问题报告留档（`user://fuse_problems_report_*.txt`），进 milestone 归档——下次对比增量

### 竞态"确认无害"的情形

预警是静态分析，有合法的写写场景：互斥分支内写同一变量（IfElse 两支各写一次）、初始化 Trigger 与重置 Trigger 分属不同生命周期阶段。这类在拓扑里看清楚执行路径确实互斥后可放过——但**默认按有事处理**，确认互斥的责任在你。

## 常见问题

### 竞态预警很多，从哪条开始？

从 GLOBAL 变量的写写开始（共享面最大），SCOPE 的最后看。变量监视器录制一段实际游戏过程，观察预警变量的真实写入序列，能快速分辨真冲突与误报。

### 用了并行条件评估，竞态会变多吗？

不会。并行的是**条件评估**（只读判断），指令执行与变量写入的路径不变——这也正是条件"只读契约"（见[自定义条件最佳实践](custom_condition.md)）存在的意义。

### Runner 的 `run()` 手动调用和事件触发撞车？

手动调用属于"代码侧写者"参与竞态。代码调用同样遵循单一写者原则：让代码侧调用的 Runner 成为该变量的唯一写者，其余单元只读。
