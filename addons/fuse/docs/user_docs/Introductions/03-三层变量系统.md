# 《别让全局变量满天飞：Fuse的LOCAL/SCOPE/GLOBAL三层变量怎么管》

看完这篇，你会拿到一套判断标准：在 Fuse 里写一段逻辑时，手里的数据到底该塞进 LOCAL、SCOPE 还是 GLOBAL——选错了，轻则变量读不到、场景一切换全丢，重则存档越攒越大、游戏越跑越慢，最后几十个全局变量从开局挂到结尾，改一个牵一发动全身。如果你见过那种"所有数据都丢进全局变量"的项目，这篇能帮你从根上绕开这个坑。

## 一、先把变量的"住处"想清楚

很多新手拿到 Fuse，第一反应是把所有数据都设成 GLOBAL。这种想法很自然——全局变量哪都能读、哪都能写，听起来最省事。但真做起来会很快撞墙：一个受击动画算出来的临时距离值也存进全局，切换场景也不清，退出游戏还写进存档，存档文件膨胀到几兆；更要命的是命名冲突，血量叫 `hp`、敌人血量也叫 `hp`，两个 Trigger 各写各的，值被来回覆盖，调一晚上都查不出谁改了谁。

问题的根源不在 Fuse，而在于把"住处"选错了。现实里你不会把所有东西都堆客厅：草稿纸写完就扔（临时），工具箱放在工位边上随用随取（工位内共享），户口本锁进保险柜长期保存（全局持久）。Fuse 的三层变量系统就是按这个逻辑设计的——LOCAL 是草稿纸，SCOPE 是工位工具箱，GLOBAL 是保险柜。先把这条心智模型立住，后面所有的用法都是顺水推舟。

顺带说清一个常见误解：这三层不是"高低档"，没有哪层比哪层高级。它们的区别只在"这条数据该活多久、该被谁看到"。一个临时值用 GLOBAL 是浪费，一个要存档的玩家等级用 LOCAL 是灾难。判断标准永远是数据本身的性质，而不是"GLOBAL 听起来更厉害"。

## 二、三层各自住哪

先看一张全景图，把三层的边界画清楚。

![三层作用域示意图](three-layer-scope.png)
*三层作用域示意图：LOCAL 限定在单次指令序列内、SCOPE 限定在场景子树的容器节点内、GLOBAL 贯穿整个游戏进程，生命范围和访问成本从左到右递增。*

**LOCAL（局部）。** 存在执行上下文 `ExecutionContext` 里，生命周期跟着这次指令序列一起结束，序列跑完变量就没了。访问最快，因为是直接的字典查找。它只服务于"当前这一串指令"内部的中间值传递。

**SCOPE（作用域）。** 存在场景树里的 `ScopeVariableContainer` 节点上，范围是这个节点管理的子树。同一个子树里的多个 Trigger、多个 Runner 可以共享读写。子树节点销毁时变量自动清理，不会泄漏到场景之外。它是 LOCAL 和 GLOBAL 之间的折中。

**GLOBAL（全局）。** 存在 `GlobalVariableManager` 这个进程级单例里，游戏运行期间一直活着，跨场景共享。配合存档系统可以做持久化，是唯一能跟着存档文件落盘的层。

一句话记住边界：**LOCAL 用完即弃、SCOPE 子树共享、GLOBAL 进程常驻**。三层的访问速度也是这个顺序递减——LOCAL 最快，SCOPE 次之（要查容器节点），GLOBAL 最慢（要走单例管理器）。

还有个细节值得提前知道：三层的读写都走统一的 `VariableOperations`，提供 `get_variable`、`set_variable`、`has_variable` 三个方法，第一参数都是执行上下文 `context`，第二是变量名，第三指定作用域。同一套接口、同一套写法，区别只在那个作用域枚举值。这意味着你在指令之间切换作用域几乎零成本，不用改调用方式。

## 三、LOCAL：临时数据该去的地方

LOCAL 最常见的误用，是把"中间计算结果"也塞进 GLOBAL。比如算两点距离、累计一次伤害、记一个循环计数器——这些数据当下算完当下用完，没有任何理由让它活到游戏结束。

下面是一个受击伤害的完整小案例。角色被击中时，根据攻击力和防御力算出实际伤害，存到 LOCAL，紧接着的指令读它去扣血、飘字、加击退——全程不碰 GLOBAL：

1. 在 Runner 的指令序列里放一个 **SetVariable** 指令，`scope` 选 LOCAL，`variable_name` 填 `temp_damage`，`value` 用表达式算出（攻击力减去防御力，表达式写法下一篇详讲）。
2. 后面接一个 **MathOperation** 指令，读 LOCAL 的 `hp` 减去 `temp_damage`，结果还是写回 LOCAL。<!-- 修正：Fuse 不存在 ModifyVariable 指令，变量间的数学运算应使用 MathOperation。 -->
3. 再接 **SetUIText**，把 `temp_damage` 拼成飘字显示在屏幕上。
4. 序列跑完，`temp_damage` 自动消失，存档里干干净净。

这种写法的好处是显而易见的：临时值不会污染存档、不会和别的 Trigger 同名变量打架、访问还最快。判定一条数据该不该用 LOCAL 很简单——**问一句"序列跑完还需要它吗"，不需要，就 LOCAL**。

需要特别提醒的是循环计数器。Fuse 的 ForLoop 指令每轮都会产生当前索引、当前元素这些临时值，它们天然就该走 LOCAL。如果你发现自己把循环计数器写进了 GLOBAL，那基本可以断定是选型失误。

再补一条容易踩的坑：LOCAL 变量名即便和 GLOBAL 同名也互不干扰，因为它们压根存在两个不同的字典里。但反过来这也提醒你——如果你以为在写 LOCAL、其实把作用域下拉成了 GLOBAL，变量会一直留着且全局可见，下一关还在。这是排查"变量没被清掉"这类 bug 时第一个该查的点。

## 四、SCOPE：场景内共享与继承链

LOCAL 只能在一个指令序列里活着，但很多时候你需要在"同一个场景的几个节点之间"共享一份数据——比如 UI 血条、计分板、魔法槽都要读角色的当前血量。这时候 LOCAL 太窄、GLOBAL 又太宽，SCOPE 正好卡在中间。

做法是在 UI 的根节点上挂一个 `ScopeVariableContainer` 节点，给它一个 `scope_id`（比如叫 `ui`）。然后这个容器子树里的 HPBar、ScoreDisplay、ManaBar，任何一条指令读写 SCOPE 变量时，默认会找到最近的这个容器：

```
GameUI (ScopeVariableContainer, scope_id: "ui")
├── HPBar     (指令：写 hp = 100)
├── ScoreDisplay (指令：读 hp 决定是否低血量告警)
└── ManaBar   (指令：读 hp 同步血条宽度)
```

场景切走、GameUI 被销毁时，这份数据自动清掉，不会残留到下一关。这是它比 GLOBAL 高明的地方——生命周期和场景绑定，干净利落。

**四种来源，精准定位容器。** 当场景树里同时有多个容器（比如玩家面板和敌人面板各一个），指令需要指定去哪个读。Fuse 给了四种 `scope_source`：NEAREST 取最近的容器（默认）、CUSTOM_ID 按 `scope_id` 精确指定、TRIGGER_SCOPE 取触发器节点所在的容器、TARGET_NODE 取目标节点所在的容器。选 CUSTOM_ID 时再填一个 `custom_scope_id`，就能跨子树精确读写，不会读串。

![SCOPE 来源选择](scope-source.png)
*SCOPE 来源选择截图：选择 CUSTOM_ID 后填入 custom_scope_id，指令会跨子树精准定位到指定容器，避免在多容器场景里读串数据。*

**继承链：子容器读父容器的变量。** 这是 SCOPE 最容易被忽略、却最有用的一项能力。容器可以配置继承模式：NONE 不继承、READ_ONLY 只读继承父容器、READ_WRITE 读写继承父容器。这样就能搭出"全局配置 → 关卡局部覆盖"的结构。

看一个游戏难度的实战。根节点放一个容器 `game_settings`，存难度系数、最大血量这些全局设定，继承模式设成 READ_WRITE；每一关再放一个子容器 `level1`、`level2`，继承模式设成 READ_ONLY。关卡里的指令读 `difficulty` 时，本地没有就顺着继承链往上找，拿到 `game_settings` 的值；如果某关想临时提高难度，直接在自己的容器里写一个同名变量覆盖，只影响这一关，改完不动全局。这是一种结构化的配置管理方式，比把所有难度参数都塞 GLOBAL 要可控得多。

继承链还有个实战上的讲究：读取是"就近向上"，写回却要看继承模式。READ_ONLY 的子容器只能读父级，写同名变量会在自己本地建一份，不会动到父级——这正是"关卡覆盖全局"能成立的前提。READ_WRITE 则是写穿透，子容器直接改父级，适合那种"子节点就是要改全局设定"的场景。把这两种模式用对，整套配置就有了清晰的读写边界。

## 五、GLOBAL：跨场景与多存档槽位

GLOBAL 是最重的一层，也是唯一能持久化落盘的层。它负责两件事：跨场景共享状态，以及存档读档。

跨场景共享很好理解。玩家在村庄场景里的等级、经验、背包，切到战斗场景后必须还在——这些数据只能放 GLOBAL。配合 CompareVariable 这类条件指令，你还能做"血量低于 30 触发低血量警告"这类跨场景判断。

真正让 GLOBAL 强大的是它配套的存档系统。Fuse 提供了 **SaveGlobalVariables**（存档）和 **LoadGlobalVariables**（读档）两个指令，配合 `GlobalVariableAssistant` 节点，能搭出完整的多存档槽位流程。来看一个 RPG 多槽位存档的完整案例：

先做存档写入。放一个 Trigger，事件绑快捷键 S：

1. **SetVariable** 指令，scope 选 GLOBAL，`variable_name` 填 `current_save_slot`，`value` 写成 `user://saves/slot_01.tres`——记下当前用的是哪个槽位。
2. **SaveGlobalVariables** 指令，`save_target` 选 CUSTOM_PATH，`custom_path` 填 `user://saves/slot_01.tres`，`save_scope` 选 PERSISTENT_ONLY。
3. 接一个 **Print** 打印"已保存到存档槽 1"。<!-- 修正：Fuse 调试日志指令为 Print（属性 message），不存在 LogInstruction。 -->

读档反过来，Trigger 绑快捷键 L：

1. **LoadGlobalVariables** 指令，`load_source` 选 CUSTOM_PATH，`custom_path` 填同一个 `user://saves/slot_01.tres`。
2. **Print** 打印"已从存档槽 1 加载"。<!-- 修正：同上，LogInstruction 不是有效指令名，应使用 Print。 -->

这里有个关键细节：`save_scope` 选了 PERSISTENT_ONLY。这意味着只有创建时打了 `persistent = true` 标记的变量才会进存档。玩家等级、金币、关卡进度这些该存；而冷却计时器、当前帧动画状态这种临时的全局变量，不打持久标记就不会被写进去。这条规则能让你精准控制存档体积，避免把一堆不该落盘的运行时状态也塞进文件。

多槽位就是复制这套结构，槽位 2 改成 `slot_02.tres`、槽位 3 改成 `slot_03.tres`，每个槽位独立文件，互不覆盖。读档时按玩家选的槽位号拼出路径即可。

这里要插一句关于"载入会清空"的提醒：`LoadGlobalVariables` 执行时默认会先清空当前内存里的全局变量，再从文件灌进来。这意味着读档是有破坏性的，别在游戏进行到一半随手读档，否则内存里那些还没存的进度会丢。正确做法是让读档发生在场景切换、回到主菜单这类安全时机。

![多存档槽位](save-slots.png)
*多存档槽位演示截图：每个槽位对应一个独立的 user://saves/slot_XX.tres 文件，CUSTOM_PATH 指向不同文件实现互不覆盖的多存档。*

**自动保存与变化通知。** 如果不想手动触发存档，可以在场景里挂一个 `GlobalVariableAssistant` 节点：`resource_path` 填存档路径，`auto_load_on_ready` 打开实现进游戏自动读档，`auto_save` 打开实现退出时自动存档，`auto_save_delay` 设个延迟防止高频写盘。需要谨慎的是 `auto_save_on_change`——每改一个变量就存一次盘，高频变化时性能开销很大，默认是关的，建议保持关闭、改用指令在关键节点手动存。

另一个常用能力是变化监听。`GlobalVariableManager` 会发出 `variable_changed` 信号，带 `name`、`old_value`、`new_value` 三个参数。比如玩家血量一变就触发屏幕红闪、金币一涨就更新计分板——把信号连上对应的反馈逻辑就行，不用自己轮询。Assistant 也提供 `variable_modified` 信号，在场景层更方便接。

## 六、选型对照表

把三层的决策标准归到一张表里，照着选就行：

| 数据特征 | 该用哪层 | 例子 |
|---|---|---|
| 序列内算完即用、跑完就丢 | LOCAL | 伤害中间值、循环计数、临时索引 |
| 场景内多节点共享、场景走就清 | SCOPE | UI 血量、计分板、场景局部配置 |
| 跨场景共享、需落盘持久 | GLOBAL | 等级、金币、关卡进度、设置项 |

再加一条反向的：**如果一条数据三种作用域都能用，从最窄的 LOCAL 开始试**。LOCAL 不够再升 SCOPE，SCOPE 不够才动 GLOBAL。这条原则能挡掉绝大多数"全局变量膨胀"的源头。

## 七、三条工程纪律

第一是性能。前面说过访问速度 LOCAL > SCOPE > GLOBAL，所以循环里别反复读 GLOBAL。错误写法是每次循环都 `get_variable` 读一次配置；正确写法是循环外读一次到 LOCAL，循环里只用 LOCAL 副本。几百上千次的循环里，这个差别会直接体现在帧率上。

第二是默认值兜底。`VariableOperations.get_variable` 带第四个参数 `default_value`，变量不存在时会返回它而不是报错。推荐养成习惯：每处读取都带上合理默认值，比如读玩家等级写 `1`、读分数写 `0`，这样即便变量还没初始化，逻辑也能安全往下走，不会因为一处缺值让整条指令序列中断。只有当你需要严格区分"变量不存在"和"变量值为 null"这两种情况时，才用 `has_variable` 先做存在性检查。这个细节在项目后期数据越来越多时尤其重要——一个没带默认值的读取，可能在某个边角场景把整条逻辑链打断，而你半天查不出原因。

第三是命名。规范命名能大幅降低排查成本：LOCAL 用 `temp_` 前缀（`temp_distance`、`temp_index`），SCOPE 按功能分组（`ui_hp`、`enemy_spawn_count`），GLOBAL 用描述性名字（`player_level`、`game_difficulty`）。这样以后用变量监视器（系列后面的调试篇会细讲）查问题时，一眼就能看出某个值是哪来的、属于谁。

## 八、收尾

三层变量系统的全部精髓，其实就一句话：**优先 LOCAL，必要时 SCOPE，慎用 GLOBAL**。把数据放对住处，大部分数据组织问题都能在源头解决，不用等到存档膨胀、命名冲突时再回来收拾。
