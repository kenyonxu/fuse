# 让逻辑会"思考"：Fuse 条件系统与 AND/OR/NOT 复合判断

上一篇我们把事件系统讲透了——`OnInterval`、`OnTimer`、`OnReceiveEvent` 这些事件像一双双盯着游戏世界的眼睛，时刻准备着"什么时候该动手"。但只盯"什么时候"还不够。真实游戏里，同一个事件往往需要在不同情境下做出不同反应：玩家按了攻击键，但角色正在眩晕就不能出招；敌人进入了视野，但还没到攻击距离就不会扑上来。看完这篇，你能给 Trigger 装上一个会思考的"大脑"——让它不只是"听到事件就执行"，而是"听懂事件、判断条件，再决定该不该动手"。这就是 Fuse 条件系统的全部意义。

## 条件系统全貌：55 个判断砖块

Fuse 的条件系统目前共 55 个条件，分布在 20 余个小类里：复合逻辑、变量、距离、导航、数学、字符串、数组、字典、时间、物理、节点、节点操作、输入、动画、渲染、UI、系统、场景、状态、scope。从"血量是不是低于 30%"到"敌人有没有绕到玩家背后"，从"是不是白天"到"运行平台是不是移动端"，覆盖了游戏逻辑里几乎所有"要不要做"的判断。

但数量本身不是重点。重点是条件能组合。一个独立的 `CheckDistance` 只能回答"近不近"，而真实游戏里你想要的判断往往是"近 AND 有蓝 AND 不在冷却"。Fuse 给你的不是一堆散装积木，而是一套能嵌套任意深度的复合条件体系。这才是它区别于"枚举式条件列表"的关键。

## 四个复合条件：AND/OR/NOT 的可视化版本

整个条件系统的"逻辑胶水"是这四个复合条件：

- **CheckAll**（所有条件满足）：AND 逻辑，所有子条件都为 true 整体才 true。
- **CheckAny**（任意条件满足）：OR 逻辑，任一子条件为 true 整体即 true。
- **CheckNot**（非）：NOT 逻辑，把子条件结果取反。
- **CheckComposite**（条件组合）：支持更灵活的自定义组合方式，用于搭建复杂条件树。

最关键的一条规则：**复合条件的子条件可以是任意条件，包括另一个复合条件**。这意味着你可以把一棵条件树搭到任意深度，没有层数限制。

举个最常见的"角色能否攻击"判断。玩家按了攻击键，但角色得同时满足"活着、有蓝、技能不在冷却"三个条件才能真出手。搭法是：在最外层放一个 `CheckAll`，下面挂三个子条件——`CompareVariable` 查法力值、`CheckHealthValue` 查血量、`CheckCountdownFinished` 查冷却。在 Inspector 里这是一棵可折叠的树，比代码里写 `if hp > 0 and mp >= 10 and not in_cooldown` 还直观。

`CheckAny` 适合"任一即触发"的场景。比如玩家死亡判定，三个条件——生命值小于等于 0、掉出屏幕、超时——任意一个成立就 Game Over。把它写成 CheckAny 而不是三个并列的 Trigger，逻辑更聚合，也方便统一接一个 GameOver 指令。

`CheckNot` 看似简单，实战里却非常常用。因为它能复用现成条件实现否定式判断。比如"敌人不在视野内"，与其专门去找一个"距离大于视野范围"的条件，不如直接 `CheckNot` 包一个 `CheckDistance`。一次复用，少造一个轮子。

## 嵌套：把判断搭成一棵树

真正体现复合条件威力的是嵌套。来看一个智能寻敌 AI 的判断：

```
CheckAll:                                   # 必须全部满足
  - CheckAny:                               #   敌人状态：存活 或 可复活
      - CompareHealthThreshold (hp > 0)
      - CheckVariable (revive_state == true)
  - CheckNot:                               #   且不在无敌状态
      - CheckVariable (invincible_time > 0)
  - CheckAny:                               #   且距离 或 路径任一满足
      - CheckDistance (距离 < 攻击范围)
      - CheckPathAvailable (有可达路径)
```

这棵条件树翻译成自然语言就是："敌人活着或可复活，且不处于无敌状态，且要么在攻击范围内、要么有路径能走过来时——才允许追击"。整个判断在 Inspector 里是一棵可折叠树，每个节点都能点开看参数。比起在代码里写四层嵌套的 if-else，可读性只高不低。

有两个性能细节值得记住。`CheckAll` 在遇到第一个 false 时立即短路返回，`CheckAny` 在遇到第一个 true 时也立即短路返回。所以把"最可能失败/最可能成功"的条件放前面，能省掉不必要的判断。

## 综合条件：14 个专用传感器

复合条件负责"怎么组合"，综合条件负责"判断什么"。这一组共 14 个条件，散落在多个小类，每个都是针对某一类特定判断的专用传感器。

`CheckDistance` 应该是日常用得最多的一个。它直接比较两个节点（或节点与位置）的距离，通过 `use_3d` 切换 2D/3D 计算。配合 `OnInterval` 做"每秒检测附近敌人"非常顺手。

`CheckPathAvailable` 是给 NavigationAgent 准备的——检查 agent 到目标位置有没有有效路径。塔防、RTS 这类需要判断"能不能走到"的游戏里几乎是必备。

`ExpressionCondition` 是护城河级别的存在（表达式系统在第 4 篇已详讲）。它能直接吃一个 GDScript 布尔表达式，再通过变量绑定把变量引用映射进去。一个表达式条件顶得上好几个基础比较条件。

渲染与 UI 这块有 `CheckIsOnScreen` 和 `CheckUIVisible`。前者判断节点是否在当前视口内，常用于"弹幕飞出屏幕就回收"；后者判断 UI 元素的 visible 属性，常用于"暂停菜单打开时屏蔽游戏输入"。

血量相关有两个：`CheckHealthValue` 判断"血量是否等于目标值"，`CompareHealthThreshold` 用比较运算符判断"血量与阈值的关系"。Boss 阶段切换、低血量警告这类场景用后者更合适。

字符串有两个：`CheckStringContains` 检查子串包含，`CheckStringLength` 检查长度。系统层面有 `CheckFrameRate` 和 `CheckPlatform`。

最后是 `CheckPreloadStatus`，它是场景预加载流程的关键一环——它能检查预加载处于 LOADING、LOADED 还是 FAILED 状态，是"加载完了再切换场景"的判断基础。

## 时间条件：让逻辑感知时序

时间条件共 4 个，专门解决"什么时候"的时序判断：

- **CheckTimeReached**（时间到达）：当前时间是否到了指定时间点。
- **CheckTimeRange**（时间段内）：当前时间是否在指定范围内，支持跨午夜循环。
- **CheckCountdownFinished**（倒计时结束）：倒计时是否走完。
- **CheckGameTime**（游戏时间）：与游戏运行时长比较。

`CheckTimeRange` 最经典的用法是日夜循环。比如 `start_time: 06:00`、`end_time: 18:00`（可用秒数或时间格式），开启 `wrap_around` 后还能处理"夜晚跨午夜"的情况。

`CheckCountdownFinished` 是技能冷却的标配，独立工作不绑定特定事件——释放技能时把当前时间写进变量，用条件检查"开始时间加 duration 是否已过"。

`CheckGameTime` 用于"游戏运行满 5 分钟判定胜利"这类限时模式。

## 实战：一个会判断的敌人 AI

来看一个能跑通的小案例：智能寻敌敌人。需求是每 0.5 秒检测一次，如果玩家在 15 米内、有可达路径、且技能冷却已结束，就追玩家；否则原地待命。

搭建步骤：给敌人节点挂一个 Runner，Trigger 选 `OnInterval`，`interval_seconds` 设为 0.5。在 Runner 的条件槽里放一个 `CheckAll`，下面挂 `CheckDistance`（距离 < 15）、`CheckPathAvailable`（可达路径）、`CheckCountdownFinished`（冷却结束）。条件成立时执行 `NavigateToPosition` 让敌人移动。另开一个 Runner 用 `CheckNot` 包住上述条件，条件不成立时停止追击。

跑起来后，敌人会在玩家靠近且有路可走时立刻进入追击，玩家跑远或绕到不可达区域时自动停下。

## 条件、事件、指令：三位一体的思考闭环

回头看，条件本身不做事，它只负责"判断"。真正完成动作的是指令，而触发判断的是事件。三者构成了一个完整的"思考-行动"闭环：

- 事件回答"什么时候检查"
- 条件回答"要不要做"
- 指令回答"做什么"

绝大多数游戏逻辑都能套进这个三元组。当你发现一个 Trigger 逻辑越搭越乱时，先别急着加条件，而是问自己三个问题：事件选对了吗、条件拆清楚了吗、指令串得太长了吗。

## 小结

Fuse 的条件系统不是"55 个枚举项"那么简单。它的真正价值在于四个复合条件撑起的任意深度嵌套，加上综合条件和时间条件覆盖的判断面。配合事件和指令的三元组模型，你能在可视化界面里搭出几乎任何"思考"逻辑。

判断完之后，接下来往往要动手操作游戏世界——切换场景、生成敌人、改节点属性。下一篇我们就走进 Fuse 的"手脚"：场景切换、后台加载、节点增删改，看看如何管好整个游戏世界。
