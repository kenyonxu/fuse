# 一张图看懂全场景逻辑：Fuse Topology 拓扑主屏与静态分析

上一篇我们用断点、执行追踪和变量监视器把单点调试做到了 IDE 级别。但调试有个前提——你得先知道问题出在哪个 Trigger。项目里有几十个场景、上百个 Trigger 互相通过 Event Bus 联动时，"去哪查"本身就变成了最大的成本。Fuse 的答案是给整个项目装一个上帝视角：Fuse Topology 拓扑主屏。看完这篇你会明白它不只是一张好看的图——它是一个内置的静态分析器，在你没运行游戏的时候就能把"未声明变量""NodePath 失效""写写竞态"这些问题直接标红，还能告诉你哪个 Trigger 写了变量、哪个 Trigger 读了它。可视化系统的工程化护城河，从这一屏开始成型。

## 单点调试够用，直到项目变大

上一篇的断点、追踪、监视器，本质都是"运行时"调试——跑起来才看得到。但有两类问题运行时根本抓不到：一类是"配置就错了"，比如 NodePath 指向一个不存在的节点、`EmitSignal` 引用了一个目标节点没有的信号；另一类是"逻辑结构有问题"，比如某个 local 变量只有读没有写（运行时永远拿默认值）、两个 Trigger 抢着写同一个全局变量（执行顺序未定义）。

这两类问题靠运行时调试要么抓不到，要么得复现半天才浮现。Fuse 把它们前置到了编辑阶段，工具就是 Topology 主屏。

## Topology 主屏：全场景的上帝视角

Topology 注册在编辑器顶部的 "Fuse" Tab，和 2D / 3D / Script 并列，是 Fuse 编辑器集成的顶级入口。它依赖三个文件协同：`fuse_topology.gd`（主面板）、`fuse_graph_builder.gd`（拓扑构建）、`instruction_analyzer.gd`（指令分析）。

界面是左右分栏。左侧是**Trigger 树**，扫描当前场景的所有 Trigger 和 Runner，按节点结构分组，每个 Trigger 展开后是嵌套的指令链，带图标和分支标记，第二列显示绑定的 Event。右侧是**详情面板**，用 BBCode 富文本渲染——选中 Trigger 显示概要（事件、操作节点、变量、信号、指令数），选中指令显示这条指令的参数、依赖和引用。

举一个左侧树大概的样子：

```
Trigger(OnKey)         on_key
  ├ SetVariable
  ├ CompareVariable
  └ EmitSignal
Runner(OnTimer)        timer
  └ TweenMoveTo
```

这种树形视图是现阶段的主交互方式。代码里其实还保留了一个基于 `GraphEdit` 的节点图组件（`FuseGraphEdit`、`FuseGraphNode`），但当前默认降级隐藏，仅留作备查。

## 不用手动刷新的交互设计

Topology 最舒服的一点是**自动刷新**。它在两个时机自动重建拓扑，都带 0.5 秒防抖避免频繁刷新卡顿：切换场景时，和保存场景（Ctrl+S）时。所以你的工作流就是改一改、按 Ctrl+S、抬头看一眼 Topology 标注更新了没，不需要记着去点刷新按钮。手动刷新按钮当然也还在。

配套的还有两个细节。一是**选中保持**：刷新后会自动恢复你之前选中的 Trigger 或指令，不会因为保存了一下就把你正在看的节点弹回根。二是**双击跳转**：双击 Trigger 直接让 Inspector 跳转到场景里对应的节点，你立刻就能编辑它的事件和指令配置；双击指令则让 Inspector 显示这条指令的 Resource，直接改参数。

这套交互闭环的意思是——Topology 不只是一个只读的看板，它和 Inspector、场景树是联动的。看到问题 → 双击定位 → Inspector 修 → Ctrl+S → Topology 自动刷新验证，整个回路不用离开主屏。

## 静态分析：编辑阶段就标红（护城河加重）

如果说"画一张 Trigger 树"还只是信息聚合，那**静态分析**才是 Topology 真正的护城河。每次刷新时，`InstructionAnalyzer.analyze_problems` 会跑一遍指令序列，结果就地标注在树节点上。分析覆盖五类问题：

- **local 未声明变量**：指令链里读写了某个 local 变量，但整条链（含条件嵌套分支）里没有任何 `SetVariable` 声明它。这是最常见的"为什么我的变量永远是 0"。
- **NodePath 解析失败**：指令引用的 NodePath 在当前场景里解析不到实际节点。典型于重构场景树后忘了更新指令的目标路径。
- **信号引用检测**：`EmitSignal` 引用的信号名在目标节点上根本不存在。
- **事件白名单**：有些事件（比如输入类事件）会主动向 `ExecutionContext` 注入变量，这些在白名单内的不算未声明，避免误报。
- **StatusError / StatusWarning 图标**：有问题的指令节点用红色（error）或黄色（warning）主题图标加行着色；Trigger 节点会汇总子树问题计数，比如行尾显示 `(2 错误, 1 警告)`，只要子树里有 error，整行标红。

选中任意节点，右侧详情面板会用 BBCode 分级着色显示该节点的具体问题。这五类检测的价值在于：**它们都是"配置时就能发现"的问题**，不需要你把游戏跑起来撞到才意识到。

## 跨 Trigger 关联扫描：另一种护城河（加重）

单 Trigger 内的问题靠静态分析抓，跨 Trigger 的问题靠**关联扫描**抓。Topology 详情面板会自动分析跨 Trigger 的变量和信号引用，输出四类关联：

- **写-读箭头**：Trigger A 写了变量 `x`，Trigger B 读了 `x`，详情面板标注 `x: 写入于 TriggerA → 读取于 TriggerB`。这是正常的协作关系，帮你确认数据流是不是按你预期在走。
- **写-写竞态预警**：多个 Trigger 都写同一个变量，标注 ⚠ 警告，提示执行顺序未定义。比如两个 `OnInterval` 都在改 `global:score`，谁先谁后取决于帧调度，结果可能不稳定。
- **孤写**：某个变量只有写没有读，标注提示（可能是冗余逻辑，写了没人用）。
- **孤读**：某个变量只有读没有写，标注 **error**（运行时必然拿到默认值，几乎肯定是漏写）。

这四类关联是大型项目最容易出"玄学 bug"的地方——单看每个 Trigger 都没毛病，合起来就出问题。关联扫描把它们可视化出来，是 Topology 区别于普通"节点树浏览器"的核心。

## Inspector 数据流卡片：单 Trigger 的透视镜

除了 Topology 主屏，Fuse 在 Inspector 里也塞了一张**数据流卡片**。当你选中任意 `BaseTrigger` 节点（Trigger 或 MultiEventTrigger），Inspector 底部会出现一个可折叠的数据流按钮，格式大概是 `📊 数据流: OnInterval (5指令, 3节点, 8变量, 2信号)`。

展开后是一段缩进文本，把这条 Trigger 的指令链结构摊开给你看：

```
数据流
  事件: OnInterval
  操作节点: Player, Enemy, ScoreLabel
  变量: [local] damage, cooldown | [scope] hp(../Player) | [global] score
  信号: score_changed(ScoreManager) | on_death(Player)
  指令链 (5 条)
    ┊ SetVariable → damage = 25
    ┊ CompareVariable → hp > 0 ?
    ┊ TweenMoveTo → 移动到 Enemy
    ┊ EmitSignal → score_changed
    ┊ Print → "攻击完成"
```

数据来源是 `InstructionAnalyzer.build_topology()` 的分析结果，包含事件名、引用到的所有节点路径、按 local/scope/global 分类的变量、所有 EmitSignal 引用的信号，以及扁平化的指令链。

**问题计数角标**是这个卡片的加分项。当这条 Trigger 的指令链存在静态分析问题时，`📊 数据流` 按钮会显示角标（如 `2 错误, 1 警告`，有 error 时按钮字体变红）。展开卡片后底部"问题详情"段按 error / warning 分级列出，和 Topology 主屏的标注保持一致。所以你不用切到 Topology 也能在一个 Trigger 内看到它的健康度。

## 三档过滤与导出报告

问题一多，全部显示反而看不清重点。Topology 顶部 banner 提供一个 OptionButton 三档过滤：

- **全部**：显示所有节点（默认）。
- **仅错误**：只显示含 error 的节点，隐藏无问题和纯 warning 节点，快速定位必须修的问题。
- **无**：关闭标注，纯拓扑视图，适合只想看结构不想被颜色干扰的时候。

配合 Trigger 行后缀的问题计数（`(2 错误, 1 警告)`），你能一眼定位问题集中的区域，再切到"仅错误"逐个击破。

还有一个**导出问题报告**按钮，把全场景的问题汇总写进 `user://fuse_problems_report_*.txt`。适合你没法直接盯 Topology 的场景——比如 CI 跑完导一份报告、或者把问题清单发给队友离线审查。

## 实战：把一个脏场景扫干净

拿一个真实的脏场景走一遍完整流程。假设你接手了一个原型，场景里有十几个 Trigger，运行时偶尔分数不对、偶尔某个特效不播放。

第一步，切到 "Fuse" Tab 打开 Topology。先不切过滤，扫一眼全景——看哪些 Trigger 行尾标红了，心里有个数。

第二步，banner 过滤切到"仅错误"。现在树里只剩必须修的问题。假设看到两条 error：一条是某个 `PrintVariableValue` 引用了 local 变量 `combo_count` 但没声明，一条是 `EmitSignal` 引用了 `on_death` 但目标节点没有这个信号。

第三步，双击标红的 `PrintVariableValue` 节点，Inspector 跳转到这条指令 Resource。你看一眼，确认确实是漏了声明——回到指令链顶部补一条 `SetVariable` 把 `combo_count` 初始化为 0。

第四步，双击 `EmitSignal` 节点，Inspector 显示这条指令。检查它的目标节点路径，发现路径指向了一个被重命名过的旧节点。修正 NodePath，指向现在真正挂载 `on_death` 信号的节点。

第五步，Ctrl+S 保存。Topology 自动刷新（0.5 秒防抖），两条 error 消失，选中状态自动恢复到你刚才看的位置。

第六步，过滤切回"全部"，看详情面板的跨 Trigger 关联。假设详情里提示 `global:score` 是写-写竞态（两个 Trigger 都在写），标注了 ⚠。这不是 error 但确实是个隐患——你决定把其中一个 Trigger 的写改成原子累加，或者干脆让只有一个 Trigger 拥有写权。

第七步，点"导出问题报告"，把当前还剩的 warning 清单存一份。修完一批 diff 一批，直到报告里只剩无关紧要的孤写提示。

整个过程没有运行过一次游戏，全在编辑阶段完成。

## 几个使用注意

静态分析**不是万能的**。它靠反射式提取指令里的变量引用（复用 `_extract_variables`），不是独立的类型推导引擎。所以动态拼出来的变量名（比如从字符串拼接 `local:` 前缀）它认不出来，会漏报。动态场景以运行时变量监视器为准。

GraphEdit 节点图**当前未启用**。如果你看到代码里有 `FuseGraphEdit` 别困惑，现阶段主交互是 Tree 树形视图，节点图只是保留备查。

导出问题报告路径在 `user://`，**CI 环境要确认该目录可写**。本地审查没问题，自动化流水线里要注意权限。

数据流卡片**只在选中 BaseTrigger 时出现**。选中普通节点或指令 Resource 是看不到的，别到处找。

## 小结

Fuse Topology 用一张图把全场景的 Trigger 关系、指令链、变量数据流画清楚，再叠上静态分析和跨 Trigger 关联扫描，让"配置错误"和"结构隐患"在编辑阶段就暴露。配套的 Inspector 数据流卡片、问题计数角标、三档过滤、导出报告，组成了一个从全局到单 Trigger 的完整审查链路。这是可视化系统走向工程化的关键一步——项目再大，你也有上帝视角。

调试和审查都到位了，最后一关是性能和复用。下一篇是这个系列的收尾：预设系统怎么把一套 Trigger 跨项目复用，对象池怎么让弹幕不再卡顿，场景预加载怎么消除切换卡顿，多线程条件怎么把上百个条件的判断压到毫秒级，以及 RuntimeInstance 怎么让多个 Trigger 并发互不干扰。把 Fuse 真正用到生产级。
